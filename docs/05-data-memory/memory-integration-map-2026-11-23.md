> التاريخ: **2026-11-23 (UTC)** · الأساس: التدقيق المرافق `evo-memory-audit-2026-11-23.md` (كود فعلي، قراءة فقط)
> **سجل التصويب (2026-11-24 — بأمر المالك):** (1) تصحيح تاريخ الوثيقة واسم ملفها والإحالة إلى اسم التدقيق المصوب — كان التاريخ يحمل يوم جلسة الوكيل UTC+8 بينما الإنشاء والالتزام الفعلي 2026-11-23T20:31Z (نفس نمط تصويب دفعة 5)؛ (2) توضيح أن المتابعات والقياسات في EVO **بنية غير مفعّلة** لا ميزة إنتاجية نشطة (§2)؛ (3) ربط المثال الفردي (E2) بضوابط تجريد الهوية قبل أي دخول للمستوى ب (§2)؛ (4) إضافة شرط الأساس المصرح (موافقة العميل/أساس موثق) إلى تدفق G-3 (§3) وقرار معلق جديد رقم 5 (§5).

## 3. الفجوات الخمس الحاسمة (بترتيب الأولوية)

1. **G-1 — خزان ذاكرة العميل (R1):** نمط `evo_memory` كاملًا (استخراج كل N رسالة، قائمة حرمان، ≤300 حرف، فئات، إلغاء تنشيط، حذف أدمن موثق فقط) على مخزن مملوك، خارج المستودع العام نهائيًا.
2. **G-2 — دورة التجميع الأسبوعية المملوكة:** نمط E1/E2/E3 يعمل على بيانات المصدر الأساسي **عبر واجهاته الرسمية** (قائمة D-15 بلا PII)، ويكتب معرفة مجمعة مجهولة إلى المستوى ب — دون أي كتابة في EVO؛ والمثال الفردي (E2) لا يدخل المستوى ب إلا خلف ضوابط التجريد والبوابة.
3. **G-3 — تدفق أمثلة التدريب:** تغذية راجعة + خطط معتمدة + تعديلات → **تحقق الأساس المصرح لاستخدام بيانات كل عميل (موافقة صريحة موثقة أو أساس موثق يقرره المالك — إزالة الاسم وحدها لا تكفي)** → مرشّحات مجهولة → بوابة G-EX بشروطها الستة → مجموعات معتمدة موقعة بإصدار وبصمة.
4. **G-4 — منحنى الجودة التشغيلي:** نمط `evo_eval_runs` بعد أول نشر (أسئلة مرجعية AR/EN على البرومبت الحقيقي، قاضٍ رخيص، أمان + مطابقة لغة).
5. **G-5 — وصفة التصدير/الاستيراد الكامل:** `export --all` بصيغ مفتوحة + اختبار استيراد في بيئة نظيفة خلال ساعة (مهمة phase-05 م5-4 المخططة).

## 4. القابل للنقل دون تعديل جوهري (نسخ كود مملوك + اختبارات)

| الوحدة | المصدر | لماذا تنتقل كما هي |
|---|---|---|
| `normalizeForMemory` · `isDuplicateMemoryFact` · `validateMemoryFacts` · `sanitizeStoredFacts` · `capTranscriptForExtraction` · `buildEvoMemoryPrompt` · `formatEvoMemoryForPrompt` · `shouldExtractMemory` | `src/lib/evo-memory.ts` | نقية بلا أي تبعية خارجية؛ سلوكها محدد بالثوابت المصدرة |
| `classifyGoal` · `normalizeFoodName` · `aggregateNutritionPatterns` · `buildExemplarSkeleton` · `pickExemplarSource` · `diffFoodNames` · `mergeSwapPayload` · `buildPlatformKnowledgeBlock` · `buildSwapLearningBlock` | `src/lib/evo-nutrition-learning.ts` | نقية (تستورد التطبيع من evo-memory فقط)؛ مصادرها تمر عبر types معرفة من المتصل |
| `isFollowupDue` · `buildFollowupPrefWrite` | `src/lib/evo-followup.ts` | نقية بحتة |
| `parseEvoFeedbackInput` | `src/lib/evo-feedback.ts` | نقية بحتة |

التعديلات الوحيدة المطلوبة على أيٍّ منها:
1. فصل طبقة الوصول للتخزين (واجهة Repository بدل `supabaseAdmin`) — المجمّع والقواعد تبقى نقية.
2. توحيد الطوابع على UTC (متوافق أصلًا مع ADR-0013).
3. إسقاط أسماء الجداول على عقد المصدر الأساسي (القائمة البيضاء D-15) بلا أي كتابة في EVO.
4. اختبارات الوحدة مرافقة لكل وحدة (نمط `src/lib/__tests__` في EVO، وبنفس روح فحوص الطفرة 26/26 هنا).

**ما لا يُنقل:** أي جدول أو صف بيانات مستخدمين؛ أي كود مرتبط بـSupabase مباشرة (استبداله بواجهة)؛ أي سير عمل GHA يعمل داخل مستودع EVO (نظيره يُنشأ في AlkemosAI).

## 5. قرارات معلقة على المالك تفتح بعد موافقة هذه الخطة

1. اعتماد بنية المستويات الثلاثة + بوابة G-EX (وثيقة الخطة المرافقة).
2. اعتماد نقل الوحدات النقية المذكورة أعلاه إلى `AlkemosAI/engine/` (كود مملوك داخل المستودع الخاص).
3. تحديد إيقاع دورة التجميع: أسبوعي (مطابق لـEVO، تكلفة صفر) أم يومي بعد اكتمال M2.
4. تحديد ثابت N للاستخراج في R1 (EVO تستخدم 10 — الترشح: البدء بها).
5. **اعتماد نص شرط الأساس المصرح لبيانات العملاء (جديد — تصويب 2026-11-24):** صيغة موافقة العميل ومكان التقاطها واحترام الانسحاب (أو الأساس الموثق البديل) قبل فتح تدفق G-3 — شرط G-EX الثالث يتوقف على هذا الاعتماد.
