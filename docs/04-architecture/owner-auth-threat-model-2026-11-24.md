# مصادقة المالك: نموذج التهديد وحدود الثقة ودورة حياة المفاتيح

> إصدار: v1.0 · تاريخ: 2026-11-24 (UTC) · الدفعة: 16 (هوية المالك وأمانها — أمر المالك) · المرجع التنفيذي: `engine/settings.py` · `engine/owner_auth.py` · `engine/auth.py` · الاختبارات: `scripts/test_engine_owner_auth.py` (57/57) + `scripts/test_engine_security.py` (84/84 — منها 9 لتزوير الهوية الواقعي)

## 1. هوية المالك الأساسية الوحيدة

- **الاعتماد (أمر المالك — دفعة 16):** `speerr@gmail.com` هي هوية المالك الأساسية **الوحيدة** في إعدادات المحرك — `engine/settings.py: OWNER_EMAIL_PRIMARY`.
- **البريد هوية معلنة لا سر:** يسكن إعدادات المحرك علنًا (ليس سرًّا ولا يُعامل كذلك — SECURITY §1). الأسرار الفعلية: كلمة المرور، رمز التحقق، رموز الاستعادة، والمفتاحان (§4).
- **الإنفاذ:** خدمة مصادقة المالك (`engine/owner_auth.py`) لا تنشئ حسابًا ولا تقبل دخولًا ولا استعادةً إلا لهذا البريد؛ الرسائل موحدة (anti-enumeration)؛ والحساب المخزن ببريد آخر يُرفض عند التحميل (لا مصالحة صامتة). تغيير هوية المالك الأساسية = قرار مالك موثق (DECISIONS) لا متغير بيئة قابل للتلويث.
- كل رمز مالك تسكّه الخدمة يحمل `sub` = البريد الأساسي ويوقّع **بمفتاح المالك المستقل** حصرًا.

## 2. آلية المصادقة (بريد + كلمة مرور + رمز تحقق عبر البريد) — بلا واجهة

طبقة خدمة للمضيف فقط — **لا صفحات ولا مسارات HTTP ولا قوالب في هذه الدفعة** (أمر المالك: دون افتراض وجود واجهة مستخدم حاليًا). أي واجهة مستقبلية تُربط بمحول خارج المحرك يستهلك العقود في §5.

### 2.1 التدفق

1. **الإعداد الأول (مرة واحدة):** `bootstrap_owner(password)` — ينشئ الحساب الوحيد للبريد الأساسي، ويعيد **رموز الاستعادة الثمانية مرة واحدة** (تُخزن بصماتها sha256 لا نصوصها). bootstrap ثانٍ مرفوض دائمًا.
2. **الدخول — الخطوة الأولى:** `begin_login(email, password)` — scrypt بالملح المخزن، مقارنة زمن-ثابت:
   - كلمة صحيحة + سياسة رمز البريد مفعلة (الافتراضي) → يُصدر رمز 6 أرقام عمره 10 دقائق ويُسلّم للمضيف مرة واحدة (`delivery_code` في النتيجة، أو عبر `email_sender` محقون فلا يعود في النتيجة) — **المحرك لا يرسل بريدًا** (قانون الاستقلالية §1): قناة التسليم مسؤولية المضيف.
   - كلمة صحيحة + `require_email_code=False` → هوية كاملة فورًا (سياسة أخفض للمضيف).
   - أي فشل → رسالة موحدة «بيانات اعتماد غير صالحة» + عدّاد يتصاعد.
3. **الدخول — الخطوة الثانية:** `complete_login(email, code)` — الرمز أحادي الاستخدام، بصمته تُقارن زمن-ثابت، 5 محاولات خاطئة تُبطله (يُطلب جديد)، والمنتهي يُرفض.
4. **الناتج:** هوية مالك موثقة كاملة (`Principal` + رمز owner موقع بمفتاح المالك المستقل) — نفس عقد `TokenAuthority.verify`.

### 2.2 سياسات الأمان (أرقام وحدة قابلة للحقن في الاختبارات)

| السياسة | القيمة | الموازنة |
|---|---|---|
| تخزين كلمة المرور | scrypt (n=2^15, r=8, p=1, dklen=64) + ملح 16 بايت | صعوبة ذاكرة ضد تسريع العتاد؛ السجل يحمل معاملاته فلا تنكسر سجلات قديمة عند ترقية المعاملات |
| رمز البريد | 6 أرقام · عمر 10 دقائق · أحادي الاستخدام · يُخزن sha256+ملح | حد 5 محاولات قبل إبطاله؛ إصدار جديد يبطل المعلق القديم |
| القفل التدريجي | 5 إخفاقات (كلمة مرور أو رمز استعادة) → قفل 300 ثانية يتضاعف حتى سقف 3600 ثانية | العدادات في المخزن فتبقى عبر إعادة التشغيل |
| كلمة المرور (سياسة) | ≥12 حرفًا · لا تحوي البريد أو جزئه المحلي · سقف 1024 | رفض من المصدر |
| رموز الاستعادة | 8 رموز 20 حرفًا سداسيًا · أحادية الاستخدام · بصمات فقط | تُولد من جديد بعد كل استعادة (القديمة تبطل جميعًا) |
| anti-enumeration | رسالة واحدة موحدة لكل الفشلات | البريد الأساسي معلن أصلًا — لكن لا تتسرب أي إشارة حالة حساب |

### 2.3 حدود مصادقة المالك (موثقة بصدق)

- **قناة البريد خارج المحرك:** اعتراض البريد = مسؤولية المضيف/مزود البريد — الرمز عامل ثانٍ لا خط دفاع أول (كلمة المرور لازمة قبله).
- **لا تقييد IP/جهاز:** خارج نطاق طبقة المحرك (قرار مستقبلي للمضيف/الواجهة إن طُلب).
- **الرموز في القيمة المرجعة:** عند غياب `email_sender` يعود الرمز في النتيجة للمضيف — مقصود (المحرك بلا مزود بريد)؛ الواجهة المستقبلية يجب أن تحقن `email_sender` فلا يعود الرمز في أي قيمة مرجعة.

## 3. الصلاحيات واستعادة الوصول وإدارة بيانات المصادقة

### 3.1 من يحكم الحساب (بوابة `_require_owner_action`)

كل عملية حساسة على الحساب (تغيير كلمة المرور · تدوير رموز الاستعادة) تقتضي **ثلاثة شروط معًا**:
1. **إثبات كريبتوغرافي:** `TokenAuthority.attest(principal) == True` (الشهادة على الحقول الحاكمة بمفتاح المالك — §5.2). **الهوية المبنية بنيويًا (تجاوز الإغلاق بلا مفتاح) تُرفض هنا** — هذا هو تطبيق «معالجة تزوير Principal وفق نموذج تهديد واقعي».
2. **نوع المالك:** `kind == owner` (لا خدمة/أدمن/عميل — سقوف أنواع الطبقة كلها).
3. **البريد الأساسي نفسه:** `principal_id == OWNER_EMAIL_PRIMARY` (رمز مالك بمعرّف آخر لا يحكم الحساب) + عمر غير منته.

### 3.2 استعادة الوصول (كلمة المرور مفقودة)

`recover_access(email, recovery_code, new_password)` — معاملة واحدة تحت القفل:
- رمز استعادة صحيح (بصمة مقارنة زمن-ثابت) → يُستهلك (أحادي)؛ خاطئ → رسالة موحدة + يغذي عدّاد القفل (استنزاف الرموز بالتجربة يُقفل كالدخول).
- كلمة المرور تستبدل، أي رمز بريد معلق يبطل، القفل والعدادات تصفَّر.
- **رموز استعادة جديدة تولد** (القديمة كلها تبطل) وتُعرض مرة واحدة.
- ملاحظة الأمان: سارق ملف الحساب + بصمات الرموز لا يستطيع استخدامها (يحتاج النصوص الأصلية التي لا تُخزن)؛ سارق نصوص الرموز يستطيع — لهذا تُخزن نسختها لدى المالك في مدير كلمات المرور خارج أي نظام.

### 3.3 إدارة بيانات المصادقة

- المخزن `OwnerAuthStore` (دليل خارج شجرة git — حارس fsafety · مسار مطلق إلزامي): `owner-account.json` (كتابة ذرية تحت قفل flock + بصمة تكامل ذاتية تكشف الفساد/العبث الصامت) + `owner-auth-events.jsonl` (سجل تدقيق إلحاقي لكل حدث: إنشاء/دخول/فشل/قفل/رمز/تغيير/استعادة — بلا أي نص سر).
- **الفساد صوت عالٍ:** JSON تالف أو بصمة لا تطابق → خطأ صريح؛ bootstrap فوق ملف تالف مرفوض — لا إعادة تعيين صامتة تفتح باب حساب بديل.
- الترقية المستقبلية للمعاملات: السجل يحمل معاملات scrypt فيتحقق بها حتى بعد رفع الافتراضيات.

## 4. دورة حياة المفتاحين: Owner Key وPlatform Key

**القاعدة الأم:** مفتاحان مستقلان ≥32 بايت لا يسكنان المستودع أبدًا (SECURITY §1) — والسلطة ترفض مفتاحين متطابقين أو قصيرين.

| | **Platform Key** (`ALKEMOS_MEMORY_AUTH_KEY`) | **Owner Key** (`ALKEMOS_MEMORY_OWNER_KEY`) |
|---|---|---|
| **يغطي حصرًا** | سك/تحقق رموز service·admin·client وشهادة هوياتها | سك/تحقق رموز owner · توقيع وثائق اعتماد G-EX (`owner_sign`) · شهادة هوية المالك · بوابة مصادقة المالك |
| **العزل** | انكشافه لا يمس هوية المالك (رمز owner موقع به يُرفض) | انكشافه لا يمس رموز الخدمة/العميل/الأدمن (المفتاحان لا يتبادلان الأدوار — مختبر) |
| **التوليد** | `python3 -c "import secrets; print(secrets.token_hex(32))"` (أو `openssl rand -hex 32`) — مرة واحدة لكل بيئة | نفس الأمر — **قيمة مختلفة تمامًا** عن مفتاح المنصة |
| **التخزين** | (أ) متغير بيئة خادم التشغيل، أو (ب) ملف خارج المستودع يُشار إليه بـ`file:<مسار>` بصلاحية `0600` (مثال `~/.alkemos/keys/platform.key` — الملف خارج أي شجرة git) | نفس الأسلوب (مثال `~/.alkemos/keys/owner.key` بصلاحية `0600`) — **بالإضافة** نسخة في مدير كلمات المرور (الاسترداد §4.5) |
| **البث/النسخ الاحتياطي** | مدير كلمات المرور الخاص بالمالك | مدير كلمات المرور + (اختياري) نسخة ورقية بعيدًا عن الأجهزة |
| **الاستخدام** | `TokenAuthority.from_env()` يقرأ المتغير/الملف — لا قيمة افتراضية داخلية إطلاقًا | نفسه + أداة المالك وحدها توقع به (بوابة G-EX تستلم `OwnerVerifier` **تحقق-فقط**) |
| **التدوير** | تدوير بسيط: رموز النوعات الثلاثة القديمة تفشل فور التحقق (أقصى عمر 7 أيام يحد الأثر) ثم تُسك من جديد | قرار مالك موثق: رموز المالك القديمة تفشل؛ وثائق G-EX القديمة موقعة بالمفتاح القديم — للتحقق الأثري أبقِ المفتاح القديم في `~/.alkemos/keys/archive/` (قراءة-فقط، للتVERIFY ببناء سلطة تحقق مؤقتة) — لا للتوقيع أبدًا |
| **الاسترداد عند الفقد** | نسخة مدير كلمات المرور؛ وإن فُقدت كليًا: ولّد مفتاحًا جديدًا (يُبطل الرموز القديمة فقط — لا بيانات تُفقد) | نسخة مدير كلمات المرور؛ وإن فُقدت كليًا: **هوية المالك القديمة (رموز وتوقيعات G-EX القائمة) تصير غير قابلة للتحقق بالمفتاح الجديد** — الحل الموثق: أرشفة المفتاح القديم قبل إتلافه، وإعادة اعتماد ما يلزم بتوقيع جديد بقرار مالك |
| **الانكشاف (الاشتباه)** | §2 SECURITY: توقف فورًا، تدوير من المزود، توثيق بلا قيمة السر | نفس القاعدة — مع أولوية أعلى (مفتاح المالك يوقّع اعتمادات G-EX وأوامر الحذف النهائي) |

### 4.5 ما لا يُستعاد بالمفاتيح (موثق بصدق)

- كلمة مرور المالك المنسية → **رموز الاستعادة** (§3.2) لا المفاتيح.
- المفتاحان ليسا في أي نسخة داخل المستودع/GitHub Secrets إلا لسير موثق يلتزم قواعد §8.6 (R-35/§8.6 — لا سير يمس المحرك يحتاجهما أصلًا: كل الاختبارات بمفاتيح عشوائية في الذاكرة).

## 5. نموذج التهديد الواقعي لتزوير Principal — والإغلاق ليس حدًّا أمنيًا

**القاعدة الصريحة:** إغلاق Python (`closure`) وخصوصية الكائنات **ليست حدودًا أمنية ولا تُدَّعى كذلك**. المهاجم داخل العملية يستطيع: قراءة خلايا الإغلاق (`Principal.__init__.__closure__`) لاستخراج مفتاح الإنشاء، واستخدام `object.__setattr__` لتعديل الكائنات المتجمدة، وبناء كائن متين بنيويًا بالكامل. لهذا:

### 5.1 طبقات المهاجمين والحسم

| المهاجم | القدرة | الحد الحاسم | النتيجة في الكود |
|---|---|---|---|
| خارج العملية: توكن مزور/معدل/منتهي/مصعّد | لا مفاتيح | توقيع HMAC + سقف النوع + النطاق + العمر | مرفوض (`verify`) |
| خارج العملية: يعرف `client_id` بلا هوية | لا هوية | نطاق الهوية (عزل بنوي) | مرفوض (`MemoryService`/السجل) |
| **داخل العملية بلا مفاتيح: يبني كائن هوية عبر `__closure__`/`object.__setattr__`** | كائنات لا مفاتيح | **الشهادة الكريبتوغرافية `attest`** | **مرفوض في كل المسارات الحساسة** (مصادقة المالك): الكائن يعبر الفحص البنيوي (`is_verified_principal`) — وهذا **موثق كحد معلن لا كدفاع** — لكن شهادته لا تطابق HMAC المفتاح فتُرفض |
| داخل العملية **ويقرأ المفتاح** من كائن السلطة | كل شيء | **خارج النطاق: حد العملية نفسه** | لا يوجد دفاع داخل Python خالص — العلاج تشغيلي: عزل العملية (حاوية)، أقل صلاحية للعملية، مراقبة؛ البوابة الكريبتوغرافية ترفع الكلفة وتحصر الوصول بمن يملك المفتاح فعلًا |

### 5.2 الشهادة الكريبتوغرافية (`_attestation` / `TokenAuthority.attest`)

- كل هوية تُنشأ من `verify` تحمل شهادة HMAC-SHA256 على الحقول الحاكمة (iss·sub·kind·clients·perms·exp) **بالمفتاح المطابق للنوع** (مفتاح المالك لرموز owner · مفتاح المنصة لما عداها).
- `attest(principal)` يعيد حسابها ويقارن زمن-ثابت — **الأمن يتبع حيازة المفتاح لا هوية كائنات Python**: تعديل أي حقل (ترقية أدمن إلى مالك) أو استبدال الشهادة نفسها يبطلها فورًا (مختبر).
- الإغلاق الداخلي (`_creation_key` + منع الوراثة + منع التعديل) يبقى **حارس صحة واستخدام سليم** (يمنع البناء العرضي بهوية حرة) — لا حد أمني.

### 5.3 ما يقبل ضمن حدود الثقة المعلنة (بصيغة فحوص موثقة)

- كائن هوية مبني داخل العملية (بلا مفتاح) **يعبر** البوابة البنيوية `MemoryService`/سجل الموافقات — الحد البنيوي ليس كريبتوغرافيًا وهم لا يملكون المفاتيح (أقل صلاحية). هذا مقصود وموثق (فحص «حدود الثقة (موثق)» في `test_engine_security.py`) — الدفاع عن هذه الواجهة هو حد العملية.
- أي مكان **تحسم فيه المفاتيح** (مصادقة المالك · سك الرموز · توقيع G-EX) يرفض الكائن المبني بلا مفتاح.

## 6. مراجعة حدود الثقة بين المكونات

| الحد (من ← إلى) | ما يعبره | ما يتحقق عند الحد | ما يُفترض (موثق) | الفشل الظاهر |
|---|---|---|---|---|
| المضيف → **TokenAuthority** | نص رمز موقّع | توقيع HMAC بمفتاح النوع + مصدر + عمر + سقف نوع + نطاق | المفاتيح من بيئة خارج المستودع (من تملك المفتاح تملك السلطة — §4) | `AuthError` موحد لا يميز السبب |
| **TokenAuthority** → **MemoryService** | كائن `Principal` | بوابة بنيوية `is_verified_principal` (النوع بذاته وصفاته مكتملة — لا نص ولا كائن مزيف) | الهوية وصلت من `verify` داخل العملية الموثوقة؛ **MemoryService لا يحمل أي مفتاح** (أقل صلاحية) فلا يملك تحققًا كريبتوغرافيًا — حد العملية يحرس هذا الحد | `MemoryServiceError`/`AccessDenied` يوثق من حاول |
| **TokenAuthority** → **ConsentLedger** | كائن `Principal` | نفس البوابة البنيوية + صلاحية `consent:*` + نطاق يغطي العميل + عمر حي | نفس افتراض العملية الموثوقة؛ **السجل لا يحمل مفاتيح** — الأساس مصدر الحقيقة الوحيد وfail-closed بدونه | `ConsentLedgerError` بلا كشف مرجع قبل التحقق |
| **TokenAuthority** → **OwnerVerifier** (البوابة G-EX) | مفتاح المالك (للتحقق) | التحقق زمن-ثابت بتوقيع مقيد ببصمة المحتوى والأصل | **تحقق-فقط**: لا قدرة توقيع في الكائن (أزيلت `sign` — كانت تناقض حد الثقة المعلن)؛ التوقيع من أداة المالك وحدها | `verify` → False فتُغلق البوابة (fail-closed) |
| **TokenAuthority** → **OwnerAuthService** (مصادقة المالك) | سلطة كاملة (سك+تحقق+attest) + مخزن المستوى أ | كلمة المرور scrypt · رمز البريد بصمته · رموز الاستعادة بصماتها · بوابة `_require_owner_action` (attest + kind owner + البريد الأساسي) | المضيف موثوق لتسليم الرمز عبر بريده؛ المخزن خارج المستودع؛ المفاتيح خارج المستودع | رسالة موحدة + قفل تدريجي + سجل تدقيق كامل |
| **OwnerAuthService** → المضيف/الواجهة المستقبلية | قواميس JSON-قابلة-للتمثيل + `Principal` + رمز owner | قناع `status()` بقائمة مفاتيح آمنة معلنة (بلا بصمات ولا نصوص سرية) | قناة البريد مسؤولية المضيف؛ الرمز في القيمة المرجعة فقط عند غياب `email_sender` | — |

**ملاحظة حدود عامة:** كل مكون يحمل أقل ما يحتاجه — البوابة G-EX: `OwnerVerifier` تحقق-فقط · `MemoryService`/`ConsentLedger`: لا مفاتيح · `OwnerAuthService`: المفاتيح عبر السلطة فقط. الحد الكريبتوغرافي الوحيد داخل العملية يملكه حاملو المفاتيح (TokenAuthority/OwnerAuthService)، وحد العملية هو الحد الأعلى للجميع (§5.1 الصف الرابع).

## 7. عقد الربط بواجهة مستقبلية (بلا واجهة الآن)

- كل عمليات الخدمة ترجع قواميس قابلة للتمثيل JSON (`status` · `code_required` · `authenticated` · `bootstrapped` · `password_changed` · `access_recovered` · `recovery_codes_rotated`) — الواجهة تستهلكها كما هي؛ `status()` قائمة مفاتيحها معلنة وآمنة للعرض.
- النقاط المتروكة للمضيف (محول خارج المحرك): تسليم رمز البريد (`email_sender`) · تعريب/عرض الرسائل · أي تقييد IP/جهاز · جلسات الواجهة (رمز المحرك `token` هو عقد الجلسة الخام).
- لا شيء في هذه الدفعة ينشئ صفحات أو مسارات أو قوالب — الأمر المالك صريح، والتدشين التشغيلي كله معزول ضمن D-17 كما هو.
