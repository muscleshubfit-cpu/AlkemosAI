# المرحلة 3 — التشغيل والبنية التحتية

> إصدار: v0.9 (مبدوءة) · تاريخ: 2026-11-22 · **الحالة: 🟡 فحص AWS منجز — قرار الاستضافة معلق على D-2/D-3** · التبعيات: المرحلة 0 ✅

## 1. الهدف

تحديد أفضل استضافة ومعمارية لتشغيل AlkemosAI وفق احتياجات كل مرحلة: الأقل تكلفة والأكثر قابلية للتوسع والنقل، دون افتراض أي حل مسبقًا (وليس Lightsail بالضرورة)، مع حماية إنتاج Alkemos.

## 2. ما أُنجز: فحص الواقع (التقرير الكامل: [`aws-audit.md`](aws-audit.md))

- الحساب مقيد بـSCP منظمة خارجية: **EC2/GPU محجوب**، Lightsail محصور في us-east-1/eu-north-1، Bedrock متاح للفهرسة (59 نموذجًا بمنطقتنا منها gpt-oss وQwen3).
- التكلفة الفعلية $0/شهر (رصيد $100 حتى 2027-04-09)، والمثيل الإنتاجي `micro_3_0` ‏1GB RAM — **لا يصلح لأي استدلال ذاتي** (حتى نموذج 4B مكمّم يستهلك ذاكرته كلها).

## 3. مقارنة خيارات الاستضافة (الأولية — بأسعار نوفمبر 2026 الموثقة)

| الخيار | التكلفة النموذجية | مزايا | عيوب | الحكم الأولي |
|---|---|---|---|---|
| **GPU مؤجرة عند الطلب (RunPod/Vast)** | 4090: $0.34/س [مُقيس 2026-11-12] | أرخص GPU · بلا التزام · واجهة OpenAI عبر vLLM بسرعة | ليس دائمًا · جودة السوق متفاوتة (Vast) | **خيار التقييم وأول إنتاج تجريبي** |
| **GPU شبه دائمة (RunPod Pods محفوظة)** | ~$55-80/شهر (عند 30-40% تشغيل) | ثبات النقطة النهائية | أغلى من الطلب الصرف | مرحلة L2 المستقرة |
| **Bedrock (eu-north-1)** | بالاستخدام (غير مُسعّر لدينا بعد) [غير متحقق] | داخل AWS ومنطقتنا · بلا تشغيل | **ليس ملكية** · مدفوع | طبقة انتقالية اختيارية (D-6) |
| **VPS بذاكرة كبيرة + CPU (llama.cpp)** | $8-20/شهر (Hetzner/Contabo 16-32GB) [موثق عام] | رخيص جدًا ودائم | سرعة CPU: ~5-15 توكن/ث لـ8B [موثق عام] — يكفي مهام خلفية لا محادثة | للمهام غير العاجلة فقط |
| **Lightsail ترقية داخل AWS** | من $12 (large_3_0 ‏2GB) لأعلى | داخل بيئتنا | SCP يحصر المناطق · لا GPU في Lightsail · **يشارك مثيل الإنتاج العنقود/الخطر** | غير موصى به للاستدلال |
| **EC2 GPU داخل AWS** | محجوب بـSCP حاليًا | — | — | يُعاد تقييمه فقط بعد D-3 |
| **Serverless GPU (Modal/RunPod Serverless)** | بالثانية + بارد عند الصفر | مثالي للانفجارات | كلفة باردة/سخونة | لل مهام الدفعية المتقطعة |

**نمط التشغيل الموصى به مبدئيًا:** حوسبة عند الطلب للتقييم والتدريب (ساعات محدودة) + نقطة نهاية شبه دائمة واحدة عند الانتقال للإنتاج التجريبي + طبقة خدمية صغيرة دائمة (توجيه/ذاكرة) على VPS رخيص أو المنصة الحالية. **قابلية النقل إلزامية: كل شيء في حاويات + IaC + بيانات في مخزن نملكه.**

## 4. المهام التفصيلية

1. ✅ فحص AWS الكامل + توصياته الأمنية.
2. ✅ مقارنة أولية للخيارات بأسعار موثقة.
3. ⬜ حسم D-3 (منظمة AWS) ثم D-2 (الميزانية).
4. ⬜ **تمرين قابلية النقل (تعريف للنجاح):** تشغيل نفس حاوية vLLM على مزودين مختلفين بنفس التكوين خلال يوم عمل واحد + استعادة من نسخة احتياطية كاملة لبيانات المحرك في ساعة.
5. ⬜ تصميم مخطط التشغيل v1: متطلبات الذاكرة/التخزين/الشبكة لكل نموذج مرشح + سقوف الإنفاق + مراقبة (عدادات تكلفة بنمط ai-usage-meter الموروث).
6. ⬜ تحديد سياسة النسخ الاحتياطي: أوزان النماذج (مرة عند التنزيل) + بيانات/ذاكرة (يوميًا) خارج مزود التشغيل (مبدأ «نسخة خارج كل مزود» الموروث من استراتيجية نسخ Alkemos).
7. ⬜ قياس فعلي (عند فتح الميزانية): توكن/ثانية، زمن أول توكن، تكلفة/مليون توكن لكل خيار معتمد.

## 5. معايير النجاح

- قرار استضافة موثق بالأرقام يشمل: تكلفة ساعة GPU فعلية، تكلفة/مليون توكن مقيسة، زمن أول توكن P50/P95، خطة تراجع.
- تمرير تمرين قابلية النقل (§4.4).

## 6. الأوامر المرجعية (تُنفَّذ عند فتح المرحلة)

```bash
# تشغيل نقطة نهاية متوافقة مع OpenAI على GPU مؤجرة (vLLM)
docker run --gpus all -p 8000:8000 vllm/vllm-openai \
  --model <المرشح> --max-model-len 16384 --quantization <حسب النموذج>
# قياس الإنتاجية والزمن
python bench/bench_serving.py --base-url http://<gpu>:8000 --dataset benches/our_tasks.jsonl
# (بدائل CPU للتقييم الرخيص)
ollama run <model>  # أو llama.cpp server
```
